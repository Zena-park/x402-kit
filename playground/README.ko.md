# x402-kit playground

x402-kit이 실제로 어떻게 쓰이는지 **한 명령으로 눈앞에서 돌려보는** 데모입니다.
로컬 anvil 체인 위에서 판매자·구매자·facilitator가 진짜 결제를 주고받습니다.
외부 네트워크로는 아무것도 나가지 않습니다.

## 실행

```bash
# 요구사항: Node 20+, foundry (anvil/cast/forge)
npm install
npm run playground          # A → B → C 전부
npm run playground -- b     # 특정 장만 (a | b | b2 | c)
```

## 결제 시나리오 지도 — 실세계 결제가 x402에 어떻게 대응되나

실세계 결제는 크게 네 갈래로 나뉩니다. 각 시나리오가 어느 챕터에서 실제로
돌아가는지, 아직 안 되는 건 왜인지를 함께 표시했습니다.

**A군 — 온라인 건별 결제** (요청할 때마다 한 건씩)

| # | 시나리오 | 상태 |
|---|---|---|
| S1 | 에이전트/앱이 유료 API 호출 — 402 받고 서명해서 재시도 | ▶ **A장에서 실행** |
| S2 | 사람이 콘텐츠·상품 단건 구매 — S1과 와이어 동일, 서명 UX(패스키 지갑)만 다름 | A장 해설 |
| S3 | 미배포 스마트월렛의 생애 첫 결제 (ERC-6492) | 지원 — 별도 settler 컨트랙트 배포 필요라 데모 밖 |
| S4 | EIP-3009 없는 **평범한 ERC-20**으로 결제 — Permit2 경유, 최초 1회 approve 뒤 서명만 | ▶ **A장에서 실행** (데모 결제 전부가 이 permit2 경로) |

**B군 — 대면 결제 (POS)** (계산대에서 온체인 확정을 기다릴 수 없다)

| # | 시나리오 | 상태 |
|---|---|---|
| S5 | QR 제시형 — POS가 결제 조건을 QR로, 손님 폰이 서명. **verify=승인(즉시·무료) → 물건 인도 → settle=매입(비동기)**. 카드의 승인/매입 분리와 동형 | ▶ **B장에서 실행** |
| S6 | 금액 미확정 대면(주유·보증금) — 상한 서명, 실액 정산 | ▶ **B2장에서 실행** (`upto`) |
| S7 | 완전 오프라인 (양쪽 다 통신 불가) — verify에 온체인 조회가 필요해 **이중지불을 막을 수 없음** | ✖ 범위 밖 (정직한 한계) |
| S8 | 취소·환불 — 매입 전엔 settle 안 하면 끝(무비용), 매입 후엔 역방향 결제 | B장 해설 (환불 헬퍼는 예정) |

**C군 — 반복 결제** (권한을 한 번 걸고, 판매자가 주기마다 청구)

| # | 시나리오 | 상태 |
|---|---|---|
| S9 | 고정 구독 (넷플릭스형) — 회차별 결제를 **한 번의 서명 절차**로 미리 만들어 맡김 | ▶ **C장에서 실행** |
| S10 | 변동 후불(통신비·공공요금 — 상한 내 임의 금액 청구) | 미구현 — 지불자의 스마트월렛이 상한을 강제하는 계정층 방식으로 설계 중 |
| S11 | 할부 — S9와 같은 메커니즘, 값만 다름 (회차금액 × n) | C장 해설 |
| S12 | 해지 — 스케줄은 판매자에게 중단 통지로 충분(서명 총액 이상은 원래 안 나감; 잔여 회차의 온체인 무효화는 Permit2 직접 호출로 가능, 킷 헬퍼는 예정), 계정층은 지갑의 권한 취소 그 자체 | 스케줄: 가능 · 계정층: 설계 중 |
| S13 | 에이전트 예산 위임 — "이 에이전트가 월 X까지 알아서 결제" (M2M의 상위 모델) | 미구현 (계정층) |

**D군 — 선불** (충전형)

| # | 시나리오 | 상태 |
|---|---|---|
| S14 | 선불지갑/기프트카드 — **토큰 잔액이 곧 선불지갑**이고, 판매자가 자기 발행 토큰으로 받으면 기프트카드 | A장이 이미 이 모형 (해설 참조) |
| S15 | 대중교통 (버스·지하철 탭) — 탭은 이용 기록(오프체인)으로 두고 **일 단위 집계를 상한부로 청구** (후불교통형) | 미구현 — S10과 같은 계정층 방식의 특수형 |

## 챕터

| 장 | 시나리오 | 쓰이는 API |
|---|---|---|
| **A** `a-online.ts` | S1 · S4 (+S2·S14 해설) | `withPaywall` · `permit2Terms` · `wrapFetch` · `approvePermit2` |
| **B** `b-pos.ts` | S5 (+S8 해설) | `buildPaymentRequired` · 코덱 · `signPayment` · `FacilitatorClient` |
| **B2** `b2-upto.ts` | S6 | `uptoTerms` · `/supported`의 `facilitatorAddress` · `signPayment` · settle 시 `amount`=실액 |
| **C** `c-schedule.ts` | S9 (+S11·S10 해설) | `signPaymentSchedule` · `validateSchedule` · `dueEntries` · `chargeScheduled` |

## 읽는 법

각 장의 `.ts` 파일이 곧 그 주제의 사용법 문서입니다 — 위에서 아래로 읽으세요.
데모 토큰은 `e2e/contracts/TestToken.sol`("Test KRW Stablecoin"/TKRW)이고, 모든
결제는 x402 스펙의 permit2 이체 방식(캐노니컬 Permit2 + `x402ExactPermit2Proxy`,
Base 실배포 바이트코드)을 탑니다 — 이 경로는 토큰의 EIP-3009 기능을 전혀 쓰지
않으므로, **평범한 ERC-20이어도 완전히 동일하게 동작**합니다. (데모 토큰이
3009도 갖고 있는 건 e2e 하니스와 공용이라서일 뿐입니다.)

시간 워프(`anvil.increaseTime`)는 데모 전용입니다 — 실전에서는 그냥 시간이
흐르고, 판매자의 크론이 `dueEntries`로 도래 회차를 골라 청구합니다.
